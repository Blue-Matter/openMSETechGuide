2  Overview of openMSE

The purpose of this chapter is to familiarize users with the terminology and names of the primary objects and functions that are used in openMSE. Later sections and chapters of this manual provide more details for these components, including detailed examples.

2.1 OOP and S4 Classes

openMSE is designed with an object-oriented programming (OOP) paradigm using R’s S4 system, where the code is organized around objects, which contain relevant data, and functions (methods) that operate on those objects (see Advanced R for more details on OOP and S4 in R).

2.2 Primary Objects and Functions

Figure 2.1 shows an overview of the MSE process in openMSE, with colors indicating the primary objects and the functions.

2.2.1 The OM Object

The Operating Model (OM) object is the main component of the MSE framework. It describes the characteristics of a fishery system and contains all the information required to simulate the population and fleet dynamics, the collection of fishery data, and the application of management procedures.

OM objects are built from four sub-components, with an optional fifth sub-component:

  1. Stock: an object describing the biological characteristics of the stock(s) in the OM;
  2. Fleet: an object describing the properties of the fleet(s) in the OM;
  3. Obs: an object describing the observation error model used to generate data from the OM (typically one per stock and fleet);
  4. Imp: an object describing the implementation error model used for implementing management advice into the OM (typically one per stock and fleet);
  5. An optional Data object containing observed historical data from the fishery. When provided, this data is used for the historical fishery data in thw OM, and is used to condition the Obs object(s) so that simulated observations in the projection period maintain the same statistical properties as the historical data. If no Data object is provided, fishery data are generated using the observation error model described in Obs.

2.2.2 Simulate and the Hist Object

The Simulate function takes an OM object, simulates the historical fishery described in that OM, and returns a Hist class object.

Simulate also does several other things including:

  • calculate reference points (e.g., unfished, MSY ref. points);

  • optimize for a specified depletion level (if applicable);

  • condition the Obs model on the provided Data object (where applicable);

  • generate simulated fishery data from the Obs model (where applicable).

The Hist object contains the simulated historical fishery dynamics, including the historical fishery data (either real observed data or data generated by the model), and the biological reference points. It is used to project the model forward in time for each management procedure.

2.2.3 The Data Object

The Data class is used in two distinct roles within openMSE.

As an input to the OM (optional): a Data object can contain real observed historical data from the fishery. When provided, this data is used directly as the historical fishery data and is also used to condition the Obs model. Conditioning ensures that the simulated observations generated during the projection period maintain the same statistical properties (e.g., observation error variance and bias) as the historical data.

As a dynamic container for MP functions: during the projection period, a Data object is populated each time step with the latest simulated fishery observations generated by the Obs model. This is the object that MP functions receive as their primary argument and use to generate management advice. It contains both the real historical observations (from the historical period) and the model-generated observations (from the projection period to date).

2.2.4 Management Procedure (MP) Functions and the Advice Object

A Management Procedure (MP) is a set of rules that defines how a fishery will be managed. These rules can range from simple harvest policies to more complex arrangements.

In openMSE, MPs are defined as special R functions that take a Data object as their primary argument and return an Advice object containing the management regulations to be implemented into the fishery.

In each time step of the projection period, the Data object is updated with new simulated observations generated by the Obs model. The MP function is then applied to this updated Data object, and the resulting Advice object is implemented back into the fishery dynamics, accounting for any implementation error described in the Imp model. This feedback loop – generate data, apply MP, implement management advice – repeats for every time step and every MP being evaluated.

2.2.5 Project and the MSE Object

The Project function runs the closed-loop simulation described above across all time steps and all specified MP functions. It takes a Hist object and one or more MP functions as its primary arguments, and returns an MSE class object once the projection period is complete.

MSE objects contain the fishery dynamics from both the historical period (carried over from Hist) and the projection period during which the MPs were applied, enabling direct comparison of management procedure performance across simulations.

2.3 Constructors, Accessors, and Assignment Functions

openMSE provides three families of functions for working with S4 objects: constructors, accessors, and assignment functions.

2.3.1 Constructors

Constructor functions create new objects of a given class. Each primary object class has a matching constructor function of the same name:

myOM    <- OM(Name = 'My Operating Model')
myStock <- Stock(Name = 'My Stock')
myFleet <- Fleet(Name = 'My Fleet')
myObs   <- Obs(Name = 'My Observation Model')
myImp   <- Imp(Name = 'My Implementation Model')
myData  <- Data(Name = 'My Data')
NoteA Note on Object Classes

The names of the openMSE 2.0 S4 object classes are actually all lowercase, for example:

class(OM())
[1] "om"
attr(,"package")
[1] "MSEtool"

The reason for this is that these object classes are designed to replace legacy classes (see Appendix B) which have uppercase names (e.g., OM, Hist, MSE).

However, because users rarely need to access the classes directly, and the constructor, accessor, and assignment functions for the openMSE 2.0 S4 classes use uppercase letters (e.g., OM() to create an om class object), we refer to the objects throughout the documentation by the uppercase names (e.g., Figure 2.1).

The legacy classes still exist for backwards compatibility, but are not discussed in this manual (except for Appendix B).

2.3.2 Accessors

Accessor functions retrieve the value of a slot from an object. They share their name with the slot they access:

Name(myOM)     # retrieve the Name slot from an OM object
[1] "My Operating Model"
nSim(myOM)     # retrieve the number of simulations
[1] 48

Accessors also work on nested objects. For example, Stock(myOM) returns the Stock object stored inside myOM, and from that you can retrieve sub-components (see later chapters for information on SRR and other sub-components):

SRR(Stock(myOM))    # retrieve the SRR from the Stock inside an OM

myOM |> Stock() |> SRR() # equivalent using pipes

2.3.3 Assignment Functions

Assignment functions update the value of a slot. They use R’s standard replacement-function syntax (<-):

Name(myOM)    <- 'Updated Operating Model'
nSim(myOM)   <- 100
Stock(myOM)  <- myStock
Fleet(myOM)  <- myFleet

2.3.4 Why You Should Use Assignment Functions Instead of @

R’s S4 system allows direct slot access using the @ operator (analogous to $ for lists). While it is possible to read and write slots this way, we recommend that you don’t use @ to assign values in openMSE.

Many slots in openMSE objects are derived from or depend on other slots. Assignment functions can trigger the necessary recalculations to keep the object consistent. Direct @ assignment updates only the one slot, potentially leaving the rest of the object in an inconsistent state.

For example, changing the number of age classes via the Ages sub-object requires that all age-structured arrays (growth schedules, selectivity ogives, etc.) be updated to match. The assignment function handles this; @ does not:

# Correct: assignment function ensures derived arrays are updated
Ages(Stock(myOM)) <- Ages(MaxAge = 40)

# Dangerous: only the Ages slot is changed; length-at-age, 
# weight-at-age, selectivity arrays, etc. are NOT updated
myOM@Stock@Ages <- Ages(MaxAge = 40)
Important

Always use the provided accessor and assignment functions to interact with openMSE objects. Avoid using @ for assignment. Reading slots with @ for quick inspection at the console is generally harmless, but any code you intend to keep or share should use the accessor functions for consistency and robustness.
